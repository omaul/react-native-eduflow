# Советник по контенту и педагогике

Этот документ — справочник при создании и редактировании образовательного контента. Сверяйся с ним перед работой с текстом, структурой заметок и интерактивными элементами.

---

## Философия

- **Контент должен помогать запоминать**, а не просто информировать.
- **Уважай время читателя.** Каждое предложение несёт пользу или убирается.
- **Пробивай четвёртую стену.** Контент может обращаться к читателю, задавать вопросы, провоцировать размышления.
- **От простого к сложному.** Никогда не предполагай, что читатель уже знает термин, если он не был введён ранее.

---

## Педагогические принципы

### 1. Chunking (дробление)

Разбивай материал на маленькие, самодостаточные блоки:
- Одна заметка = одна идея или один навык
- Если заметка требует скролла больше 3 экранов — подумай о разделении
- Каждый блок должен иметь понятный заголовок-вывод

**Пример:** Вместо одной заметки "Всё о субстратах" → четыре: "Что такое субстрат", "Грунт vs субстрат", "Зачем рыхлость", "Стресс при пересадке"

### 2. Scaffolding (опоры)

Выстраивай лестницу от известного к новому:
- В начале заметки — контекст: что читатель уже знает, что узнает
- Новые термины вводи через знакомые аналогии
- В конце — краткий вывод и связь с другими заметками

**Шаблон введения:**
```
Мы уже знаем, что [известный факт].
Но что происходит, когда [новая ситуация]?
В этой заметке разберём [тема] и поймём [практический вывод].
```

### 3. Elaborative interrogation (вопросы-провокации)

Вместо утверждений — задавай вопросы, которые заставляют думать:
- "Как ты думаешь, почему корни гниют в плотном грунте?" (перед объяснением)
- "Вспомни: что общего у губки и субстрата?" (аналогия)
- Вопросы ставь ДО ответа, чтобы мозг начал искать связи

### 4. Spaced repetition (интервальное повторение)

Ключевые идеи должны встречаться в нескольких заметках:
- Повторяй важные концепции в новом контексте
- Используй перекрёстные ссылки между заметками
- В начале новой заметки — короткое напоминание связанной идеи

### 5. Concrete examples (конкретные примеры)

Каждую абстрактную идею сопровождай конкретным примером:
- Плохо: "Субстрат обеспечивает аэрацию корней"
- Хорошо: "Представь: корни в плотной глине — как дышать через подушку. Рыхлый субстрат — как дышать через марлю"

## Пробитие четвёртой стены

Контент может напрямую взаимодействовать с читателем. Вот паттерны:

### Прямое обращение
Используй "ты" (не "вы" — дружелюбный тон):
- "Попробуй угадать, прежде чем читать дальше"
- "Если у тебя дома есть фиалка — посмотри на её горшок прямо сейчас"

### Квизы и проверки
Основная форма — контейнер: заголовок в скобках это вопрос, тело блока — ответ.
```md
:::quiz[Почему торф со временем уплотняется?]
Он постепенно разлагается, частицы становятся мельче и заполняют воздушные карманы.
:::
```
Ответ скрыт до нажатия «Показать ответ». Можно добавить подсказку — она видна до раскрытия:
```md
:::quiz[Почему корни гниют в плотном грунте?]{hint="подумай про воздух"}
Без аэрации подавляется полезная микрофлора и начинаются процессы гниения.
:::
```
Однострочная форма тоже работает, удобна для коротких ответов:
```md
<quiz question="Что такое субстрат?" answer="Среда, в которой расположены корни растения" />
```
Квиз — не экзамен, а приглашение подумать. Тон ответа — дружелюбный.

### Callout-блоки
Для акцентов, предупреждений, интересных фактов:
```md
:::callout[Интересно]
Кокосовое волокно удерживает воду в 8 раз больше собственного веса
:::

:::callout[Осторожно]
Никогда не используй землю с улицы для комнатных растений
:::
```

Цвет и иконка выбираются по заголовку — отдельно указывать ничего не нужно:

| Заголовок | Вид |
|-----------|-----|
| Важно, Внимание, Осторожно | предупреждение |
| Не делай, Не используй, Никогда, Опасно, Ошибка | запрет |
| Интересно, На заметку, Запомни, Подсказка, Совет | информация |
| Готово, Хорошо, Работает | успех |

Незнакомый заголовок даёт вариант «информация». Переопределить можно так:
`:::callout[Свой заголовок]{variant="danger"}` — доступны `info`, `warning`, `danger`, `success`.

### Spoiler / раскрывающийся блок
Для ответов на вопросы или дополнительной информации:
```md
:::spoiler[Ответ]
Корни дышат кислородом из воздушных карманов в субстрате
:::
```

### Интерактивные симуляции
Физические модели, с которыми читатель играет руками:
```md
<sim name="sponge-jar" />
```
С подписью:
```md
:::sim[Ваза с губками и шариками]{name="sponge-jar"}
Пояснение под симуляцией.
:::
```
Доступные симуляции перечислены в `src/components/md/sims/registry.ts`. Сейчас есть `sponge-jar` — полив субстратов разного состава (клеточная физика на p5).

Симуляция должна доказывать вывод текста, а не украшать его. Если из неё нельзя сделать наблюдение, которого нет в тексте, — она не нужна.

### Связи между заметками
В конце заметки — блок "Что дальше?":
```md
## Что дальше?
- Теперь ты знаешь, что такое субстрат. Дальше разберём [почему рыхлость важна](#/note/care/medium/why-loose)
- Если хочешь вернуться к основам — [определения](#/note/care/medium/definitions)
- Разобрать компоненты по одному — [библиотека компонентов](#/components)
```

**Формат ссылок важен.** Приложение работает на HashRouter, поэтому внутренние ссылки в markdown начинаются с `#/`:

| Куда | Ссылка |
|------|--------|
| Заметка | `#/note/care/medium/why-loose` |
| Библиотека растений | `#/plants` |
| Карточка растения | `#/plants/monstera-deliciosa` |
| Библиотека компонентов | `#/components` |
| Карточка компонента | `#/components/perlite` |

Ссылка без `#` будет обработана как относительный путь к файлу и сломается. Тест `catalogIntegrity` проверяет, что все `#/note/...` ведут на существующие заметки.

### Ограничение синтаксиса
Директивы (`:::`) распознаются только на верхнем уровне документа — вложить callout внутрь списка или цитаты нельзя. Внутри код-блоков директивы не срабатывают, поэтому синтаксис можно спокойно документировать в самих заметках.

## Структура заметки

### Обязательные элементы

1. **Заголовок** — понятный, конкретный. Не "Субстрат", а "Почему субстрат должен быть рыхлым"
2. **Вступление** (2-3 предложения) — контекст + зачем это знать
3. **Основное содержание** — с подзаголовками, короткими параграфами
4. **Вывод / резюме** — одно предложение с главной мыслью
5. **Связи** — ссылки на связанные заметки

### Рекомендуемые элементы

- Вопрос-провокация в начале или середине
- Хотя бы один конкретный пример или аналогия
- Квиз (если есть что проверить)

### Длина

- Оптимально: 200-500 слов на заметку
- Если больше — подумай о разделении
- Заметка-обзор (оглавление темы) может быть короче

---

## Тональность и стиль

### Голос

- Дружелюбный, но не панибратский
- Уверенный, но не менторский
- "Ты" — не "вы"
- Допустимо: лёгкий юмор, бытовые аналогии, личные наблюдения
- Недопустимо: канцелярит, пассивный залог без причины, наукообразие ради наукообразия

### Форматирование текста

- Параграфы: 2-4 предложения максимум
- Списки: когда перечисляешь 3+ пунктов
- **Жирный** — для ключевых терминов при первом упоминании
- *Курсив* — для акцента или аналогий
- Заголовки — как вопросы ("Зачем нужна рыхлость?") или утверждения ("Рыхлость = дыхание корней")

## Организация контента

### Структура папок в content/

```
public/content/
  {тема}/                    — папка темы (например, plants)
    {подтема}/               — подтема
      {заметка}/index.md     — заметка с картинками рядом
      {заметка}.md           — простая заметка без картинок
```

### index.json

При добавлении заметки:
- `slug` совпадает с путём к файлу
- `title` — человекочитаемый, конкретный
- `description` — одно предложение, мотивирующее прочитать
- `tags` — для фильтрации и связей
- `date` — дата создания

### Порядок заметок

Внутри одной темы заметки идут от базовых к продвинутым. Это отражается в `index.json` порядком элементов массива. Подтемы упорядочиваются полем `order`.

Этот же порядок задаёт навигацию внутри заметки: полоску-таймлайн сверху и переходы «назад / дальше» снизу. Прев/некст идут сквозь границы подтем, то есть раздел читается как один путь. Ничего дополнительно прописывать не нужно — порядок в `index.json` и есть порядок курса.

## Библиотеки: растения и компоненты

Кроме заметок есть два каталога со структурированными данными:

- `public/content/species/catalog.json` — растения
- `public/content/components/catalog.json` — компоненты субстрата

Они связаны: в `substrate.prefer` и `substrate.avoid` у растения указываются `id` компонентов, и на странице компонента автоматически появляются списки «кому рекомендуется» и «кому не стоит». Именно поэтому рекомендации хранятся структурно, а не текстом.

### Как добавить растение

1. Добавь объект в `species/catalog.json`. Обязательное: `id`, `name`, `latin`, `rarity`, `difficulty`, `summary`, `light`, `water`, `humidity`.
2. Рекомендации по субстрату — через `id` из каталога компонентов, с полями `share` и `why`. Поле `why` важнее всех: оно объясняет, а не предписывает.
3. `relatedNotes` — слаги существующих заметок.
4. Если нужна текстовая статья — создай `public/content/species/<id>/index.md` и поставь `"article": true`. Статья дополняет параметры характером, историей и типичными ошибками, а не пересказывает таблицу.
5. Прогони `npm test` — тест `catalogIntegrity` проверит ссылки, дубли id и наличие файла статьи.

### Портрет растения

Фотографий в библиотеке нет — вместо них процедурный портрет, который рисуется из трёх признаков в поле `visual`. Никаких ассетов и лицензий, портрет детерминирован по `id` и несёт информацию: по нему видно, что пеперомия — низкий кустик круглых листьев, а монстера — крупные прорезанные.

```json
"visual": { "form": "clump", "leaf": "split", "palette": "green" }
```

**`form`** — архитектура роста:

| Значение | Кому |
|----------|------|
| `upright` | листья прямо от основания: сансевиерия, драцена |
| `rosette` | розетка: алоэ, хлорофитум, тилландсия |
| `clump` | кустик из черешков с крупными листьями: монстера, калатея, антуриум |
| `vine` | лиана с побегом: эпипремнум, хойя, сциндапсус |
| `tree` | ствол с кроной: фикус, крассула |
| `fern` | перистые вайи: адиантум, платицериум, замиокулькас |
| `stone` | литопсы |
| `trap` | ловушки: мухоловка |

**`leaf`** — `heart`, `split` (с прорезями), `arrow` (стрелолистный), `oval`, `round`, `strap` (узкий длинный), `spike` (толстый заострённый), `frond` (перистый), `trap`.

**`palette`** — `green`, `dark` (тёмная листва), `silver` (серебристый напыл), `grey` (литопсы).

Формы `stone`, `trap` и `fern` строят геометрию сами и `leaf` почти не используют. Цвета палитр живут в `src/components/PlantPortrait.module.css` (отдельно для светлой и тёмной темы) — это описание объекта, а не UI, поэтому они не в токенах.

В карточках портрет статичный, на странице растения — с лёгким покачиванием, которое отключается при `prefers-reduced-motion`.

### Как добавить параметр

Расширяемость заложена: чтобы новая характеристика появилась в интерфейсе, править страницы не нужно.

1. Добавь поле в тип в `src/types/catalog.ts`.
2. Добавь значение в данные.
3. Добавь одну запись в `PLANT_FIELDS` или `COMPONENT_FIELDS` в `src/utils/catalogLabels.ts` — параметр начнёт отображаться.
4. Нужен фильтр — добавь `FilterSpec` в `PLANT_FILTERS` / `COMPONENT_FILTERS` там же.

Если у части растений параметра нет — ничего страшного: поля со значением `null` в карточке просто не показываются.
